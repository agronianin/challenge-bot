# Git и рабочие копии

Читать перед изменением файлов или Git-состояния, публикацией и слиянием.

## Начало и продолжение задачи

- Любые изменения проекта выполняй в отдельной ветке задачи, по умолчанию `codex/…`. Новую задачу начинай от актуальной `develop`; незавершённую продолжай в её копии и ветке. Прямое редактирование и push в `develop`/`release` запрещены.
- Сначала проверь ветку, `git status --short --branch`, активные задачи и зависимости процессов от файлов копии. Чистое дерево не доказывает, что копия свободна. При неясной занятости считай её занятой; не переключай ветку и не меняй её файлы.
- В свободной копии перед новой задачей и созданием ветки переключись на `develop` и выполни `git pull --ff-only origin develop`. Локальные изменения и расхождение истории не перезаписывай; отказ pull не обходи — сохрани работу или выбери другую свободную копию.
- Если задача прямо продолжает существующие незакоммиченные изменения в указанной пользователем копии, не переноси их слепым pull/clone. Проверь занятость и создай ветку задачи от текущего HEAD, сохранив рабочее дерево и индекс; обновление базы выполни отдельно перед PR.
- Перед созданием копии проверь существующие соседние и временные каталоги `Challenge1`, `Challenge2` и далее. Используй свободную копию; если её нет — клонируй настроенный origin в следующий свободный `ChallengeN` рядом с проектом либо во временном каталоге. Не перезаписывай каталоги, не используй описательные суффиксы и credentials в URL/командах.
- В начале сообщи путь и ветку. Завершение задачи не разрешает удалять копию или чужую работу. Перед освобождением временной копии сохрани результат в удалённой ветке или согласованном постоянном месте; не объявляй её свободной, пока от файлов зависят процессы.

## Перед коммитом

- Добавляй только файлы задачи, без чужих изменений. Проверь `git diff --check`, `git diff --cached --check` и содержимое индекса (`git diff --cached`, `git ls-files`); вывод с подозрением на секреты просматривай локально, не пересылай в чат.
- В индексе не должно быть `.local/`, реального env, IDE-настроек, видео, приватного CSV, дампов, ключей, токенов, адресов серверов и идентификаторов окружений. Проверяй содержимое, не только расширения; `.gitignore` не защищает уже отслеживаемые файлы. Хранение и действия при утечке — [PRIVATE-DATA.md](PRIVATE-DATA.md).

## Pull Request и слияние

- Штатный путь: реализация, документация и проверки → ветка задачи → PR в `develop` → явное разрешение владельца на проверенную версию → `Squash and merge` → проверка результата и удаление ветки. Прямой push и локальный merge с последующим push в `develop` запрещены, в том числе владельцу.
- Перед PR обнови сведения через `git fetch origin`, разреши конфликты с базой и повтори затронутые проверки. Не переписывай чужие ветки. В PR укажи результат, проверки и ограничения; до merge должны пройти обязательные локальные проверки и доступный CI для последнего commit.
- Разрешение merge запрашивай после предъявления конкретного проверенного результата; существенные изменения предъявляй заново. Сливай через GitHub squash либо `gh pr merge <номер> --squash --match-head-commit <проверенный-SHA>`. Без разрешения сохраняй ветку и сообщай, что PR ожидает подтверждения.
- Не утверждай, что защита веток, hooks или CI настроены, без проверки фактических настроек репозитория.

## После слияния

- Проверь состояние PR `MERGED`, SHA принятой вершины и squash-коммита. Выполни `git fetch --prune origin` и проверь вхождение squash-коммита в `origin/develop`; ancestry исходных commits после squash не доказывает слияние.
- Удали оставшуюся удалённую ветку только если её вершина совпадает с принятой вершиной PR. Новые commits сохраняй.
- Чистую копию переключи на обновлённый `develop`. Локальную ветку удаляй только если она не используется другим worktree и её вершина совпадает с принятой вершиной PR; после этих проверок допустим `git branch -D`.
- В результате укажи PR, squash-коммит, проверки, судьбу локальной/удалённой веток и состояние копии. Merge не означает разрешения на поставку: production, SSH-поставка, разрушительные миграции и пересоздание сохраняемой БД требуют отдельного явного согласования.
