# Схема и Liquibase

- Liquibase запускается отдельно от приложения; Hibernate только проверяет схему. Команды — в [scripts/README.md](../../scripts/README.md). Перед тестами читай [правила тестирования](../../src/test/AGENTS.md).
- Перед правкой выясни по истории, тегам и сведениям о фактической поставке, была ли версия выпущена. `SNAPSHOT` сам по себе этого не доказывает; при недостатке данных отметь неопределённость до изменения применённой истории.
- До первого выпуска changelog описывает итоговую структуру: правь исходные definitions, убирай промежуточный DDL, временные объекты и устаревшие fixtures. Не поддерживай переходы между невыпущенными состояниями без конкретной сохраняемой БД.
- После фактического выпуска существующие changesets, их id, author и path неизменяемы; изменения добавляй новыми changesets следующей версии. Не обходи расхождения через дополнительные checksums, очистку истории, MARK_RAN и повторный структурный DDL.
- Changeset — одна законченная логическая операция, включая нужные столбцы, ограничения, индексы и описания. Не дроби её на технические шаги и не объединяй независимые операции. Между changesets оставляй одну пустую строку.
- Предпочитай стандартные XML change types. SQL используй при отсутствии подходящего community change type или для механизма конкретной СУБД; укажи `dbms`, причину и корректное разделение statements. Специфичные типы и выражения не становятся переносимыми от XML.
- Таблицы называй в единственном числе: `tg_user`, `chat.tg_chat_id` как PK чата, `exercise_type.name` как PK типа; упражнение связано с типами many-to-many. При смене модели синхронизируй Java-модель, импорт и fixtures.
- При создании собственных таблиц задавай remarks с назначением, для неочевидных столбцов — смысл, единицы, специальные значения и null. Проверяй реальные PostgreSQL COMMENT; объекты Liquibase остаются под его управлением.
- Каждая операция имеет проверенный автоматический/явный rollback либо явный отказ с причиной необратимости. Перед откатом проверь rollback-sql, совместимость приложения и сохранность данных; обратный DDL не восстанавливает удалённые данные, тег не заменяет backup.
- Изменённую невыпущенную схему проверяй на новой одноразовой PostgreSQL БД: пустая установка, повторный update без повторного DDL/потери данных, ограничения, defaults, справочники, индексы и комментарии. Новая версия дополнительно требует проверки обновления с выпущенной предыдущей и rollback/re-update, если откат поддерживается.
- Разрешение изменить миграции не разрешает менять рабочую БД. Для сохраняемой БД сверяй применённую историю, готовь backup и процесс обновления/переноса с проверкой строк; пересоздание и разрушительные операции требуют явного согласования. Старую БД сохраняй для возврата до открытия записи.
- Между реально выпущенными версиями обеспечивай expand → совместимые писатели и backfill со сверкой → остановка старых писателей → отдельный contract с явным допуском оператора. Учитывай INSERT/UPDATE/DELETE и окно отката; не создавай этот механизм для чистой начальной установки.
- При обновлении существующей БД ограничивай блокировки; большие переносы делай возобновляемыми пакетами. Локальный тест не доказывает отсутствие задержек под нагрузкой.
